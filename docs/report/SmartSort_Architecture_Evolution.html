SECTION 01Executive Summary

Problem

Households generate recyclable waste daily but reliably fail three steps: they cannot identify what material an item is, they have no discovery mechanism for facilities that accept it, and they cannot see whether it has value. The result is predictable — recyclables land in landfills and potential income is lost. Classification alone does not close this loop; a person holding waste needs a decision, not a label.

Solution

SmartSort is a mobile-first responsive web application — no app install, opened via an HTTPS URL. The user photographs a waste item; an AI service identifies the material; the user confirms or corrects it; and the system returns ranked nearby facilities with distance, operating hours, verification status, and an indicative value in ₹/kg. Every payout is explicitly labeled “Indicative market estimate — not an offer.”

Core product flow

Capture → Compress → Classify → Confirm → Locate → Match → Rank → Display

Core differentiation

SmartSort is not merely a waste-classification system. Its product value is the full bridge: Waste Identification + Facility Discovery + Distance + Estimated Value. The classification is the entry point; the discovery of where waste becomes worth something is the product.

SECTION 04Architecture Evolution Timeline

Stage 1

Original Proposal

Key decision: serverless AWS shape; classification service undecided between Rekognition Custom Labels and SageMaker.

Problem later found: training dependency, per-hour model hosting cost, unbounded scope. Result: everything downstream re-examined.

Stage 2

Technical Review (research-based, document-grounded)

Key decision: against current AWS docs — Custom Labels' real advantage is managed hosting, not “minimal data”; its $4/hr running-model billing is a live-demo hazard; Bedrock multimodal (Nova) available in ap-south-1 at per-request pricing was never evaluated.

Problem discovered: highest-risk component (custom model training) sat on the critical path. Result: Bedrock Nova proposed as primary classifier behind a stable Lambda abstraction; Cognito and async pipelines flagged as unnecessary; dataset = curated facilities, no scraping.

Stage 3

Claude Re-evaluation

Key decision: agreed with hybrid facility/map architecture (DynamoDB source of truth + Location for maps/geocoding) and React web frontend; sharpened service roles (Maps render, Places geocode, Haversine ranks, Routes optional).

Problem discovered: classification decision still defaulted toward Custom Labels; single-endpoint design persisted. Result: partial convergence — map and frontend decisions locked.

Stage 4

Claude Opus Refinement

Key decisions: Bedrock Converse API with tool schema (vs regex parsing); weights rebalanced 0.6/0.3/0.1; image compression added; human override made a first-class flow; Bengaluru standardized as demo city; 14-facility registry; confidence renamed “AI signal”.

Problem discovered: earlier plans under-specified the override path and payload safety. Result: implementation-ready spec with acceptance criteria.

Stage 5 — current

Final GLM Consolidated Plan (authoritative)

Key decisions: frontend-first build with swappable mock API; two Lambdas (classify-match / match-facilities); runtime validation chain regardless of schema; ranking formula unit-tested with documented crossover; fallback matrix complete; demo registry with 7×≥2 verified coverage proof.

Status: frontend implemented and verified (18/18 tests, E2E browser flow); backend fully specified, pending deployment. Result: the plan this document describes.

Pattern across all five stages Each stage removed risk rather than adding features: fewer services on the demo path, fewer unverifiable claims, more failure modes handled by design. The architecture got simpler as it got better.

SECTION 06AI Architecture Evolution

Earlier — custom-trained vision

Rekognition Custom Labels (primary candidate) or a SageMaker custom CNN.

  • Collect & label ~15–20+ photos per category (7 categories) under demo-like conditions
  • Train, then start/stop a hosted model — Custom Labels bills ≈$4/hour while running
  • SageMaker: notebook → training job → endpoint; strongest ceiling, heaviest pipeline
  • Single-class classifier: cluttered bins and multi-object scenes are out of scope
  • Post-hackathon evolution path (per original proposal), re-evaluated with real usage data

Current — Amazon Bedrock Nova Lite

  • Zero training: categories defined in prompt/schema; no dataset collection on the critical path
  • Zero hosting: on-demand API, per-request pricing (fractions of a cent per photo)
  • Multimodal: robust to clutter, multiple objects, messy real-world photos
  • Returns category + confidence signal + one-line rationale (material-composition prompt)
  • Available in ap-south-1 (Mumbai) — matches the pinned region

How classification is invoked

Bedrock Converse API
  toolConfig:  classify_waste { category: enum[7], confidence: 0..1, rationale }
  toolChoice:  forced → { tool: "classify_waste" }
  image:       base64 JPEG (browser-compressed) + material-composition prompt
  temperature: 0 (deterministic)

Validation chain (mandatory — schema ≠ guarantee):
  1. toolUse block present?            → else parse text fallback
  2. category ∈ enum?                  → else reject
  3. confidence ∈ [0,1] (clamped)?     → else 0
  4. failure path → retry ×2 → fallback model ID → manual category chips
Required caveat Bedrock's model-generated confidence is an AI signal, not a calibrated probability and not independently verified accuracy. The UI shows “AI signal: 87%” and always lets the user correct the category. No generalized accuracy claim is made or displayable.

Why this is the right hackathon trade

The MVP's risk was never model quality — it was model operations: collecting a labeled dataset by deadline, hosting a model reliably, and paying while idle. Bedrock removes all three. The original proposal itself anticipated this evolution (“move toward SageMaker/Bedrock once enough labeled data exists”) — the review simply inverted the order: start with Bedrock, earn the custom model later using the photo corpus the app archives to S3.

Real-world caseWhy the AI alone is insufficient

Design rule Confirming or overriding a category routes directly to facility matching — the backend never re-runs Bedrock for a human-corrected category (lower latency, lower cost, correct semantics). Low AI signal (< 0.6) shows a gentle “Not completely sure — please confirm the material” nudge; it never alarms and never blocks. The correction interface doubles as the manual path when the AI is entirely unavailable.

Startup story, not just UX: every user correction is a labeled training example. The override stream (archived with the S3 photo corpus) is exactly the dataset a future fine-tuned classifier would need — the product improves by being used.

Why compression helps

  • Payload safety: 10 MP phone JPEGs can exceed limits; compressed output sits far under them
  • Mobile bandwidth: an ~800 KB upload is seconds on cellular; 6 MB is a demo hazard
  • Bedrock efficiency: smaller images mean fewer image tokens — cheaper and faster inference
  • Quality is preserved for the task: 1024 px is ample for material classification
Honest limitation Client-side compression is best-effort. Quality-stepping reduces size toward ≈800 KB, but it does not mathematically guarantee every payload will be accepted: pathological images (noise-heavy textures compress poorly) can remain larger, and browsers without canvas support skip compression entirely (the original bytes are sent as fallback). Server-side payload limits remain the final guard. This is explicitly accepted as a demo-day tradeoff, not hidden.

Implementation note: canvas resize + JPEG re-encode in the browser (document.createElement('canvas') chosen over OffscreenCanvas for iOS Safari compatibility). Compression failure never blocks the flow — the app proceeds with original bytes and logs a warning.

SECTION 10Ranking Evolution

Earlier formula

0.7 × Distance  +  0.3 × Payout  +  0.1 × Verification  =  1.1

Weights summing to 1.1 meant no term was an interpretable share, the maximum achievable score was 1.1, and the “verification bonus” was effectively diluted. Caught in review; fixed, not silently patched.

Current formula

0.6 × Distance + 0.3 × Payout + 0.1 × Verification = 1.0
distance_score = max(0, 1 − distance_km / 5) · payout_score = payout / max_payout_among_eligible · verification = 1|0
ComponentDesign decision
Distance normalizationLinear to a 5 km boundary, then floored at 0 — facilities beyond 5 km are ranked lower, never hidden (flagged “>5 km” in UI)
Payout normalizationDivided by the best payout among eligible facilities for that query — scale-free across categories, self-adjusting per result set; denominator floored at 1 (no div-by-zero for free municipal drop-offs)
Verification bonusBonus, not a filter — unverified facilities rank lower and carry a visible badge but are never suppressed
Raw scoresInternal only. Users see ordered results, distance, estimated value, badges — never “0.756”, which means nothing to a household
Crossover behaviorDocumented and unit-tested: at these weights, a large payout gap can legitimately overcome a short distance gap (~2 km) — correct for bulk quantities, and the roadmap story for weight personalization

Worked example (unit-tested)

Scenario: verified facilities, plastic, max eligible payout = ₹30/kg

A: 1.0 km, ₹20/kg
   distance = 1 − 1.0/5 = 0.80 → 0.6 × 0.80 = 0.480
   payout   = 20/30 = 0.667    → 0.3 × 0.667 ≈ 0.200
   verified = 1                → 0.1 × 1    = 0.100
   SCORE = 0.780                                          ◄ ranks first

B: 2.0 km, ₹30/kg
   distance = 1 − 2.0/5 = 0.60 → 0.6 × 0.60 = 0.360
   payout   = 30/30 = 1.00     → 0.3 × 1.00 = 0.300
   verified = 1                → 0.1 × 1    = 0.100
   SCORE = 0.760

A wins: at household scale (a few kg), ₹10/kg more does not justify
double the travel. Payout CAN win — but only over larger gaps or with
bulk quantities (the documented crossover at distance-weight ≈ 0.61).

SECTION 13Why the Current Architecture Is More Practical

Framing: the current architecture is better aligned with the SmartSort MVP and the hackathon constraints — not universally superior. A SageMaker pipeline with a trained waste model is the stronger long-term ML play; it is simply the wrong 5-day play.

DimensionAssessment
Product clarityOne sentence — “photograph waste, find where it's worth something” — maps 1:1 to screens and endpoints. The earlier framing buried the discovery bridge under the classifier.
Engineering complexityOne SAM stack, two functions, one table, one bucket. Every removed service (Cognito, CloudFront, async triggers) removed a failure mode and setup hours.
AI practicalityNo dataset deadline, no model hosting, no $4/hr idle billing; rationale output demos beautifully; validation chain handles the failure modes regex parsing couldn't.
CostHackathon-spend bounded: pennies of Bedrock per photo; DynamoDB/S3/Lambda effectively free-tier at demo scale; compression reduces token cost; one Bedrock call per image by design.
ReliabilityList-first product; labeled demo-location fallback; retry→fallback-model→manual-chips ladder; empty state designed out via seed coverage — the demo cannot dead-end in a blank screen.
Hackathon feasibilityFrontend already built and verified; backend is a template deploy + seed run away. Every remaining task is mechanical, not exploratory.
SecurityLeast-privilege per function (matching Lambda literally cannot invoke Bedrock); scoped S3 writes; map API key restricted; CORS tightened after Day 1.
TestingThe ranking formula, Haversine, compression, and classifier determinism are unit-tested — the parts judges probe are the parts with proofs.
Future scalabilityThe Lambda abstraction survives model swaps (Nova → fine-tuned custom); S3 corpus + override stream feed that fine-tuning; DynamoDB key design leaves room for geohash; nothing is thrown away post-hackathon.
Where the earlier plans were genuinely stronger Custom-model classification offers a higher accuracy ceiling on domain-specific Indian waste streams; managed CloudFront distributions offer more control than Amplify's opinions; Cognito-native user accounts would jump-start retention features. These are acknowledged — and deliberately deferred, with the seams to add them back already in place.

SECTION 19Final Technical Summary

The 60–90 second technical explanation (for judges)

“SmartSort is a mobile-first responsive web application — React, Vite and TypeScript on AWS Amplify — so users just open a URL; nothing to install. You photograph a waste item; the browser compresses it to under a megabyte; Amazon Bedrock's Nova Lite classifies the material — plastic, paper, metal, glass, e-waste, organic, or other — through the Converse API with a forced tool schema, and we validate that output at runtime. Classification is at most once per image: a separate /match-facilities endpoint serves human corrections without re-invoking the model. The confirmed category plus your location — with a clearly labeled demo fallback if GPS is denied — goes to a Lambda that reads a DynamoDB registry of 14 curated Bengaluru facilities, filters by accepted category, computes Haversine distance, and ranks with a transparent, unit-tested formula: 60% distance, 30% estimated value, 10% verification trust. Results render as ranked cards with hours, contacts, and an indicative ₹/kg that is always labeled an estimate — never an offer — plus a MapLibre + Amazon Location map that's an enhancement, never a dependency. Every failure has a designed fallback, and photos archive to S3 fire-and-forget, building the training corpus for a custom model later. The whole backend is one SAM template.”

The 30–45 second non-technical explanation

“You know how you never know what to do with stuff you're throwing out — whether it can be recycled, or if it's worth money? SmartSort fixes that. You take a photo of the item. The app tells you what material it is, shows you the recycling and scrap centers near you that actually accept it, how far they are, when they're open, and roughly what it could be worth. You always confirm the category yourself — the AI is a helper, not the boss. Nothing to install: it just runs in your phone's browser.”

The one-breath product definition

SmartSort — an AI-powered responsive web platform for waste classification and recycling/reuse facility discovery: Waste → Identification → Location → Facility → Value.
